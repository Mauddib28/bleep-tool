# Advertisement Dissection (G-7.5)

BLEEP dissects the raw advertisement blobs that BlueZ exposes — `ManufacturerData`,
`ServiceData`, advertised service UUIDs, and `AdvertisingData` — into structured,
attributed, human-readable fields. It is implemented in
[`bleep/analysis/adv_dissect.py`](../analysis/adv_dissect.py).

## Design principles

1. **Lossless.** Every dissected entry preserves both its raw hex *and* a
   printable-ASCII rendering (non-printable bytes → U+FFFD). Advertisements
   occasionally carry clear text — e.g. some Bluetooth headsets embed a model or
   name string (`WH-1000XM4`) in service data — so **no captured byte is ever
   discarded** even when a structured decoder also runs.
2. **Two-source attribution.**
   - **Bluetooth SIG assigned numbers** via the shared resolvers in
     `ble_ops/common/conversion.py` and `bt_ref/utils.py` (company identifiers,
     member/service UUIDs, AD types). Generated by
     `bt_ref/update_ble_uuids.py` → `bt_ref/uuids.py`.
   - **Vendor/community fingerprints** via `bt_ref/vendor_adv_specs.py`,
     generated by `bt_ref/update_vendor_specs.py` from the public
     `device-library` project.
3. **Graceful degradation.** A protocol decoder failure (short/malformed
   payload) never drops the raw entry; the raw hex/ASCII are always returned.
4. **Self-contained.** All reference material lives inside `bleep/`. The
   updaters pull from public sources and commit generated modules; there is no
   runtime dependency on any external checkout.

## API

```python
from bleep.analysis.adv_dissect import dissect_advertisement

result = dissect_advertisement(
    manufacturer_data={0x004C: b"..."},   # {company_id: bytes}
    service_data={"0000feaa-...": b"..."}, # {uuid: bytes}
    service_uuids=["00001122-..."],         # advertised service UUIDs
    advertising_data={0x01: b"\x06"},      # {AD-type: bytes}
)
```

All arguments are optional and tolerant of D-Bus wrapper types. The result always
contains `manufacturer_data`, `service_data`, `service_uuids`, `advertising_data`
lists plus a `summary` dict (`vendors`, `protocols`). Each entry carries
`raw_hex` and `ascii`; attributed entries add `company`/`name`, `vendor_hints`,
an optional `protocol` label, and an optional `decoded` structure.

## Protocol decoders

| Protocol | Trigger | Decoded fields |
|---|---|---|
| iBeacon | ManufacturerData with the `02 15` prefix — company `0x004C` **or any company ID** | `uuid`, `major`, `minor`, `tx_power`; label `ibeacon` |
| iBeacon (compact) | ManufacturerData company `0xFFFF` carrying **exactly 5 bytes** (allowlisted framing observed on ESP32-class beacons, e.g. `000100a9c5`) | `major`, `minor`, `tx_power` (no `uuid`, set `null`); label `ibeacon_compact` |
| Apple Continuity | ManufacturerData company `0x004C` | TLV `messages` (type/name/raw, iBeacon recursed) |
| Eddystone | ServiceData UUID `FEAA` | `frame` = UID / URL (expanded) / TLM / EID; label `eddystone` |
| Eddystone (pending) | `FEAA` present in the advertised **service-UUID list** but no `FEAA` ServiceData payload captured yet | `frame: "pending"`, `confidence: "low"`, explanatory `note`; label `eddystone_pending` |

The compact and pending decoders exist for **rotating, non-connectable
beacons**: such devices frequently advertise a bare `FEAA` UUID (payload only
arrives on some rounds) and pack major/minor/tx into a vendor-specific `0xFFFF`
manufacturer blob rather than the canonical Apple layout. The compact trigger is
deliberately restricted to a CID allowlist (`0xFFFF`) so random 5-byte
manufacturer data is not misread as a beacon. A `FEAA` UUID upgrades from
`eddystone_pending` to a full `eddystone` frame on the round its ServiceData
payload is finally captured.

`format_beacon_summary(dissection)` renders a compact one-line identity tag from
these decoders for scan/survey output (e.g. `[ibeacon_compact m=1/i=169 tx=-59]
[feaa-pending]`); it returns `""` when nothing beacon-like was decoded. It is
consumed by `bleep/ble_ops/le/scan.py` and by `beacon-identification`
(see [Beacon identification](beacon_identification.md)).

## Vendor/community spec updater

`bt_ref/update_vendor_specs.py` mirrors the BT SIG updater and produces the
committed `bt_ref/vendor_adv_specs.py`. Source precedence:

1. `--local-path <checkout>` — dev-only bootstrap from a local `device-library`
   checkout.
2. Public GitHub (`BLESPloit/device-library`) — manifests enumerated via the
   git-tree API and fetched from `raw.githubusercontent.com`.
3. `bt_ref/vendor_specs_cache.json` — offline cache from a prior run.

```bash
python -m bleep.bt_ref.update_vendor_specs                 # pull from GitHub
python -m bleep.bt_ref.update_vendor_specs --local-path P  # bootstrap from a checkout
```

The generated module exposes `SERVICE_DATA_UUID16`, `SERVICE_UUID16`,
`SERVICE_UUID128`, `COMPANY_ID`, `MANUFACTURER_PREFIX`, and the full lossless
`SPECS` metadata list.

## Known UUID attribution corrections

A triple-pass review against the SIG data in `bt_ref/uuids.py` and the
`device-library` manifests found that the classifier's prior beacon/service-data
labels were misattributed. The authoritative labels now live in a single map
(`SERVICE_DATA_PROTOCOL_LABELS` in **`bt_ref/constants.py`** — the canonical UUID
reference layer, alongside `BT_SIG_BASE_UUID` and `UUID_NAMES`) that both the
dissector and the classifier import, so they cannot drift and users have one
place to find all UUID/attribution details. The base-UUID suffix and named
company identifiers (`COMPANY_ID__APPLE`, `COMPANY_ID__MICROSOFT`) are likewise
sourced from `bt_ref/constants.py` rather than hardcoded at call sites.

| UUID (16-bit) | Old label | Authoritative owner (SIG `uuids.py`) | Corrected label |
|---|---|---|---|
| `FCF1` | `find_my_beacon` | Google LLC | `google_nearby` |
| `FE0F` | `exposure_notification_v1` | Signify Netherlands B.V. (Philips Hue) | `signify_hue` |
| `FD6F` | `exposure_notification_v2` | Apple/Google Exposure Notification | `exposure_notification` |
| `FE05` | `microsoft_cdp` | CORE Transport Technologies NZ Limited | `core_transport_nz` |
| `FCC0` | (n/a) | Xiaomi Inc. | `xiaomi` |
| `FEAA` | (n/a) | Google LLC | `eddystone` |
| `FE2C` | (n/a) | Google LLC | `google_fast_pair` |

> **Microsoft CDP:** true CDP is ManufacturerData **company-id `0x0006`**
> (`device-library` "Microsoft Nearby"), *not* a service-data UUID. The
> classifier's separate `FE05`-in-advertised-UUIDs heuristic (previously labelled
> `microsoft_cdp`) is corrected to `core_transport_nz`; the STRONG LE evidence
> weight is unchanged, so classification decisions are preserved.

> **SIG vs community conflicts (`FCC0`):** the `device-library` "Google Nearby"
> manifest groups `FCC0` alongside Google's `FCF1`/`FE9F`/`FEF3`, but `FCC0` is
> registered to **Xiaomi Inc.** in the SIG tables. The authoritative
> protocol/attribution label follows SIG (`xiaomi`); the community grouping is
> still surfaced non-destructively as a `vendor_hint` ("Google Nearby") so both
> perspectives are retained. This is the general rule: **SIG owner wins the
> label, community source becomes a hint.**

## Integration points

- **Scanner** (`ble_ops/le/scan.py`): attaches an additive `adv_dissection`
  block to the persisted advertisement `decoded` payload. No schema change.
- **CLI `db show`** (`modes/db.py`): prints an "Advertisement Dissection"
  section for the device-detail command and attaches an `adv_dissection` block to
  the `--full` / `--json` / `--quiet` output. It recomputes the dissection from
  the persisted raw fields via `dissect_persisted_record()`, so devices scanned
  before G-7.5 (no stored block) are still dissected. `get_device_detail()` is
  unchanged — enrichment happens in the show command only.
- **Shared persisted-record adapter** (`analysis/adv_dissect.py`):
  `dissect_persisted_record(record)` reconstructs dissector inputs from persisted
  `devices`-row / AoI fields (`manufacturer_id`/`manufacturer_data`/
  `service_data`/`advertising_data`/`uuids`; bytes/hex/JSON/D-Bus-list tolerant;
  top-level or nested `device`) and returns the dissection or `None`. Both the
  CLI renderer and the AoI report use it, so their input handling cannot drift.
- **CLI `db report --recon`** (`modes/db.py`, DB-9): calls
  `dissect_persisted_record()` over the report's whole device selection and
  aggregates the results into the "Advertisement Data Analysis" subsection of the
  `## Reconnaissance Analytics` section — manufacturer data grouped by company id,
  service data by UUID, AD structures by type, each with a unique-payload tally,
  longest-common-byte-prefix pattern, decoded representative, and a
  repeated-payload (static/identity-leak) flag. Same decoder as `db show`, so
  per-device and aggregate views cannot diverge.
- **Classifier** (`analysis/device_type_classifier.py`): (1) relabel-only
  correction sourced from the shared map (see above); (2) **G-7.4** —
  `LEServiceDataCollector` feeds **both** `ManufacturerData` and `ServiceData`
  through `dissect_advertisement()` and emits STRONG `LE_ADVERTISING_DATA` evidence
  when a BLE-only protocol is decoded (`ibeacon`, `apple_continuity`, `eddystone`;
  set `_LE_INDICATIVE_ADV_PROTOCOLS`), so beacon-only devices classify as `le`.
  Eddystone lives in `ServiceData` (`FEAA`), so it is only reachable because
  `service_data` is passed to the dissector. Decode logic lives only here — the
  classifier does not re-implement it. A bare, undecoded company payload is not LE
  evidence (mfg-data also appears in Classic EIR).
- **AoI report** (`analysis/aoi_analyser.py`): renders an "Advertisement
  Dissection" section (via the shared adapter) with attributed entries plus raw
  hex and ASCII, and a **Device Type** provenance line (evidence source /
  `cached` / seed-vs-live) so an advertised or cached classification is never
  read as SDP/GATT-measured.
